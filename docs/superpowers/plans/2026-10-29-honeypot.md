# Honeypot Channel Implementation Plan

> **Superseded in places:** the ledger's rulings (`.superpowers/sdd/2026-10-29-honeypot/progress.md`, a local file) and the spec's "Changes after implementation" section supersede this plan where they differ, for example the in-flight timeout (15 minutes, not 2) and the case signatures (`beginCase` returns a case ID, which `endCase`, `recordAction`, `confirmAction` and `dropAction` take).

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a per-server honeypot channel. DragonBot keeps a pinned warning in it, removes ordinary accounts that post there (kick or ban), cleans up their last hour of messages, and never lets a honeypot ban reach ban sync.

**Architecture:**
- **Pure logic and in-memory tracking** go in a new `HoneypotService`, which has no `discord.js` imports. This covers who gets what, reason strings, same-case grouping, the action records the ban and remove handlers read, the skip set, a per-server lock, and the shutdown drain.
- **Discord-side work** goes in two `lib/` modules, the same way `lib/birthday-checker.ts` works:
  - `honeypot-warning.ts` reconciles the pinned warning.
  - `honeypot-enforcer.ts` handles honeypot posts.
- **Existing handlers and the web dashboard** get small, targeted changes.

**Tech Stack:** TypeScript (ESM, strict), discord.js 14.25.1, Drizzle ORM 0.44 on Neon Postgres, Next.js 16, zod 3, Vitest 3, pnpm/turbo.

**Spec:** `docs/superpowers/specs/2026-10-29-honeypot-design.md`. This was approved by Kevin on 2026-10-29. Read it before any task. Where this plan and the spec disagree, the spec wins; stop and say so.

## Global Constraints

**Warning embed:**
- Color `0xf0b232`.
- Title `⚠️ Do not post in this channel`.
- Description `If you send a message in this channel, you will be automatically kicked. There will be no exceptions.`, with `banned` replacing `kicked` for the Ban action.

**Who's exempt:**
- **Staff** have any of `PermissionFlagsBits.Administrator`, `ManageGuild`, `KickMembers` or `BanMembers`. Nothing else counts.
- **Verified** means the member has the server's `verificationRoleId` role. With no role set, nobody is verified.

**Removal:**
- `deleteMessageSeconds: 3600`.
- Ban reason: `[Honeypot] posted in #<channel-name> (msg <message-id>)`.
- Kick-mode ban reason: `[Honeypot kick] posted in #<channel-name> (msg <message-id>)`.
- Unban reason: `[Honeypot kick] unban after message cleanup`.
- Ban-sync backstop marker: `[Honeypot`.

**Timings:**

| Item | Duration | Counted from |
|---|---|---|
| Action record lifetime | 10 min | when the ban call resolves |
| Leftover sweep delay | 15 s | — |
| Late-message window | 2 min | when the ban resolves |
| In-flight timeout | 2 min | — |
| Skip-set entry lifetime | 10 min | — |
| Shutdown drain | 5 s | inside the existing 8 s deadline |
| Sync notice repeat | once per server per distinct text per 24 h | — |

**Columns on `guilds`:**
- `is_honeypot_enabled` boolean not null, default false
- `honeypot_channel_id` varchar(20)
- `honeypot_action` text, `'kick' | 'ban'`, not null, default `'kick'`
- `honeypot_warning_channel_id` varchar(20), written only by the bot
- `honeypot_warning_message_id` varchar(20), written only by the bot

**Dashboard rules:**
- The dashboard fields use the `moderation` scope.
- The two warning-ID columns are never accepted by the dashboard `PATCH`.

**Discord error codes** (`RESTJSONErrorCodes`):

| Code | Name | Meaning |
|---|---|---|
| 10008 | `UnknownMessage` | gone |
| 10003 | `UnknownChannel` | gone |
| 50001 | `MissingAccess` | can't tell; keep the stored IDs of the current warning (an old warning being removed is the exception, see Task 4 step 4) |
| 50013 | `MissingPermissions` | can't tell; same as 50001 |
| 30003 | `MaximumNumberOfPinsReachedForTheChannel` | notice |
| 10007 | `UnknownMember` | the account left |
| 10026 | `UnknownBan` | on unban, counts as success |

**Layering:**
- The new `honeypot.service.ts` never imports `discord.js`, and only uses `import type` from `@dragonbot/db`. `logging.service.ts` and `moderation.service.ts` already import `discord.js`, so `sendNotice` may build its embed in `logging.service.ts`.
- Event handlers stay thin.

**General rules:**
- No new environment variables and no new dependencies.
- Do **not** run `db:push`, `db:migrate`, or anything else against a database. Kevin applies the schema himself.
- Commit messages follow the repo's plain style ("Add …", "Fix …") with no attribution lines. Commit only the files the task names.
- Run bot tests with `pnpm --filter bot test`. To run only some files, pass their names with no `--`, for example `pnpm --filter bot test honeypot`; vitest ignores anything after `--`. Typecheck the whole workspace with `pnpm typecheck`. Both pass at baseline: 32 tests, typecheck clean.
- `index.ts` names its service locals `<thing>Service`. The honeypot ones are `honeypotService` (Task 2) and `honeypotWarning` (Task 4).
- In tests, mock Discord objects with plain objects cast through `unknown`, the way `apps/bot/tests/services/moderation.service.test.ts` does. Build API errors with `new DiscordAPIError({ code, message }, code, status, "PUT", "/x", {})`.

## Review Focus

1. **Spam wave:** several messages from one account arrive at once. The account must get exactly one ban and one log entry. *(Task 5 test "handles a burst from one account as one case")*
2. **Author already left:** Discord reports 10007 for the author. The ban still goes out by ID, and the log must not claim the last hour was cleaned up. *(Task 5 test "bans an account that already left and says so")*
3. **Dashboard turned off, bot cache stale:** no one may be removed. *(Task 5 test "re-reads settings and skips removal when the honeypot was turned off")*
4. **A mod deletes the warning:** it comes back straight away. When DragonBot deletes its own old warning, that deletion isn't logged as "Content not cached". *(Task 4 tests "reposts when the stored warning is deleted" and "does not log the bot's own warning deletion")*
5. **Honeypot configured but warning never posted:** for example, missing Send Messages. Members posting there must not be removed. *(Task 5 test "does nothing while the warning is not posted")*

- [ ] **Step 3: Implement `apps/bot/src/services/honeypot.service.ts`**

- Use plain `Map`s with explicit timestamps from `Date.now()`, and sweep expired entries whenever a method touches a map. Use `TTLCache` from `../utils/cache.js` only where a fixed lifetime fits: the skip set (600 s) and the `endCase` finish times (600 s).
- A record's lifetime is `Infinity` until `confirmAction`, then `Date.now() + RECORD_TTL_MS`.
- `wasRecentlyActioned` is true from `recordAction` until `RECORD_TTL_MS` after `confirmAction`, and `dropAction` clears it. `isWithinLateWindow` runs from `confirmAction` for `LATE_MESSAGE_WINDOW_MS`.
- `runExclusive` chains promises per key and removes the chain entry when it's idle. An error from one call must not block later calls.
- `track` adds the promise to a set and removes it in `finally`. `drain` races `Promise.allSettled` of the set against a timer.

- [ ] **Step 3: Implement `HoneypotWarningSync.sync(guildId)`**

Run the reconcile below inside `honeypot.runExclusive(guildId, …)`, wrapped in try/catch that logs `warn` and never rethrows.
1. Read `row = await guildService.getSettingsFresh(guildId)`. Return if it's null.
2. **Work out the target and the current warning.**
   - `desired` is `{ channelId, action }` when `row.isHoneypotEnabled && row.honeypotChannelId`, and null otherwise.
   - `stored` is the pair of warning IDs, or null.
3. **Get the guild:** `client.guilds.fetch(guildId)`. On an error, return quietly; the bot isn't in that server.
4. **Remove the old warning when it's no longer wanted.** This applies when `stored` exists and either `!desired` or `stored.channelId !== desired.channelId`:
   1. Fetch the old channel and message through `guild.channels.fetch` and `channel.messages.fetch`.
   2. Mark it with `markOwnDeletion(id)`, then delete it.
   3. If the result is "can't tell" (50001 or 50013), send a notice like `Couldn't remove the old honeypot warning in <#id>; please delete it by hand.`
   4. In every case, including "can't tell", call `setHoneypotWarning(guildId, null)`. There's only one stored ID pair, and keeping an old warning's IDs would stop the new channel's warning from ever being stored. The spec's "keep the stored IDs" rule covers the current warning, not an old one being removed; the spec spells this out under "Classify errors". Return if `!desired`.
5. **Fetch the honeypot channel:** `guild.channels.fetch(desired.channelId)`.
   - It must be text-based and sendable.
   - If it's gone (10003), or wrong, or can't be told (50001 or 50013), send a notice and return.
6. **When `stored` is in this channel,** fetch the message:
   - **Found:** if `embeds[0]?.description !== warningText(action)`, edit it with `{ embeds: [buildWarningEmbed(action)] }`. If it's `!pinned`, pin it. A pin failure sends a notice. Return.
   - **Gone** (10008): fall through to step 7.
   - **Can't tell:** send a notice and return.
7. **Adopt an existing warning.** Fetch `channel.messages.fetchPins({ limit: 50 })` and look for items whose `message.author.id === client.user.id` and `message.embeds[0]?.title === WARNING_TITLE`.
   - If any exist, keep the first: store its IDs and edit it if needed.
   - Delete the others, calling `markOwnDeletion` first.
   - Return.
8. **Post a new warning.**
   1. Send `{ embeds: [buildWarningEmbed(action)] }`.
   2. Store the IDs immediately.
   3. Call `pin("Honeypot warning")`. On 50013 or 30003, send a notice that names the missing **Pin Messages** permission or the pin limit.

**Notices** go through `logging.sendNotice`. They're de-duplicated per `${guildId}:${text}` with a `TTLCache` that lasts 86,400 s.

**`syncAll()`** iterates `guildService.getAllCached()` and keeps the rows where `(isHoneypotEnabled && honeypotChannelId) || honeypotWarningMessageId`. It awaits `sync` for each one in turn.
